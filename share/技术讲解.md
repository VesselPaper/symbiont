# 应用代理与负载均衡：讲透用的底稿

这份是备讲用的，比 PPT 细，比报告口语。看完要能做到两件事：一是不看稿把一条请求从浏览器讲到数据库；二是被追问时能答到配置行和实测数字上。

---

## 一、先把位置摆正

代理不是一个功能，是一个**位置**。它站在客户端和源站中间，所有请求都得先经过它。

这个位置带来三件事，按重要性排：

**策略只有一个落点。** TLS、限流、鉴权、日志、压缩、缓存、安全响应头，这些要么在代理上做一次，要么在每台后端上各做一次。后端有三台，做一次和做三次的差别不是工作量，是一致性。以后加第四台，代理上的策略自动覆盖，后端不用改。

**源站可以不出内网。** 这是代理价值的边界，也是最容易被忽略的一条。只要后端端口还映射在宿主机上，攻击者绕开代理直连后端，代理上所有策略瞬间归零。所以 `expose` 和 `ports` 的区别不是写法，是策略成不成立的前提。判断标准很硬：从公网能不能连上 8000。

**客户端只认识一个地址。** 后面有几台、换了几台、哪台在升级，客户端不需要知道，也不应该知道。这带来一个副作用——代理自己成了新的单点，后面单讲。

三个容易混的词，一句话分清：

- 正向代理替客户端办事，客户端知道自己在用代理，典型是翻墙和公司出口。
- 反向代理替服务端办事，客户端以为代理就是服务端。
- 网关是反向代理的一种角色，除了转发还接管横切关注点（TLS、限流、鉴权）。我们说"入口"就是这个意思。

## 二、一条请求到底经历了什么

从浏览器敲下回车到响应回来，中间这一段要能讲细。

**第一步，DNS 和 TCP。** 浏览器解析域名拿到 IP，跟网关的 443 建立 TCP 连接。这一步有个细节值得讲：HTTP/2 在一个连接上多路复用，多个请求共用同一条 TCP，所以首屏那几十个资源不需要开几十条连接。代价是 TCP 层的队头阻塞——一个包丢了，这条连接上所有流都等。HTTP/3 换 QUIC 就是为了解这个。

**第二步，TLS 握手。** 客户端发 ClientHello，带支持的版本、套件、SNI（要访问哪个域名）。服务端回证书链和选定套件。TLS 1.3 一次往返就能开始发数据，1.2 要两次。我们配了 `ssl_session_cache shared:SSL:10m`，回头客用会话复用，握手直接省掉。

这里有个词必须会用：**TLS 终止**。证书和私钥只在网关上有，网关解密之后到后端走明文。所以后端不需要配证书，也不需要处理加密开销。代价是内网那一段是明文——内网被认为是可信边界，这是常规取舍；如果内网也不可信，就要做 mTLS 或者重新加密。

**第三步，请求头和路由。** 网关读完请求头，按 Host 和路径决定交给谁。我们只按路径分：`/` 和 `/game/` 走本地静态文件，`/api/` 走上游地址池。

**第四步，改写头部。** 后端看到的连接来自网关，所以真实客户端信息只能靠头部带过去。`X-Real-IP` 覆盖写入，`X-Forwarded-For` 是追加写入（`$proxy_add_x_forwarded_for` 会在已有值后面接上当前地址，所以经过多层代理时会变成一串）。`X-Forwarded-Proto` 告诉后端原始协议是 https，否则后端生成的重定向会退回 http。

**第五步，挑后端并连接。** 从地址池里按策略选一台，建立连接。这一步和下一步是真正拉开差距的地方，后面单独讲。

**第六步，转发与回传。** 请求体往上送，响应体往下送。这里有一堆缓冲和超时的细节，也是最容易被讲错的地方。

**第七步，收尾。** 记日志、统计耗时、处理断连。

## 三、六个真正决定成熟度的机制

### 1. 连接复用

默认情况下，一个请求对应一次到后端的 TCP 连接。三次握手、慢启动、TLS（如果后端也加密）全都要重来一遍。并发一高，网关和后端都在花时间握手上。

keepalive 的思路是保持一组长连接，请求来了直接用。两个配置必须成对出现：

```nginx
upstream symbiont_backend {
    keepalive 16;
    ...
}
location /api/ {
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}
```

只加 `keepalive 16` 不够。nginx 转发默认用 HTTP/1.0，1.0 默认短连接；而 HTTP/1.1 默认长连接，所以必须显式把 `Connection` 清空，不然请求头里会带上 `Connection: close`，长连接池永远用不上。这是很典型的一处"配了等于没配"。

`keepalive 16` 指的是**每 worker 进程**的空闲连接数上限，不是总数。四个 worker 就是最多 64 条空闲连接。

### 2. 缓冲与流式（这里要讲准）

nginx 默认 `proxy_buffering on`。行为是：把后端的响应先收到自己的缓冲里，再慢慢发给客户端。缓冲分两级——内存里用 `proxy_buffers`（默认 8 个，每个 4k 或 8k），装不下就溢出写到 `proxy_temp_path` 的临时文件，上限 `proxy_max_temp_file_size`（默认 1024m）。

所以要讲准的一点是：**默认行为不会把 96MB 全装进内存，它会把大部分落到临时文件。** 内存不会爆，代价是多一次磁盘 IO，以及客户端开始收到第一个字节的时间被推迟。

我们实测网关内存从 35.13 MiB 到 35.93 MiB，基本不动。这能说明内存没被响应体占住，但严格说是"缓冲块小 + 溢出落盘"的结果，不是"零缓冲"。静态文件那条路径走的是 `sendfile`，直接从磁盘零拷贝给客户端，本来就不经过用户态缓冲。

如果要讲成严格的边收边转，配置是 `proxy_buffering off`。它对两类场景有实际意义：一是响应特别大（几十上百 MB，避免写临时文件），二是服务端推送（SSE、流式对话），因为缓冲会让数据攒着不发，客户端看不到"逐字出现"的效果。

顺带一提请求方向：`proxy_request_buffering` 默认 **on**，也就是先把整个请求体收完再转发给后端。上传大文件时这会让请求体先落盘，通常要关掉它改成边收边转。

### 3. 超时与重试

超时分三个，不能只设一个：

- `proxy_connect_timeout 5s`：跟后端建立连接的时间。连不上就是连不上，短一点好。
- `proxy_send_timeout 30s`：往上送数据时，两次写操作之间的间隔。
- `proxy_read_timeout 30s`：等待后端返回时，两次读操作之间的间隔。注意它管的是"多久没有新数据"，不是"整个请求多久"。后端慢慢吐数据（比如流式响应）可以远超这个值，只要没断流。

这三个数值的组合决定了系统怎么表现。我们连接给 5 秒，读给 30 秒。道理是：连不上是故障，要快速换台；算得慢是能力问题，不该提前掐断。

重试由两个参数控制：

- `proxy_next_upstream error timeout http_502 http_503 http_504`：哪些情况算失败、可以换下一台。注意 `error` 包含连接失败和连接被重置；超时算不算由 `timeout` 决定；如果响应已经开始发给客户端了，就不能再重试，只能断开。
- `proxy_next_upstream_tries 2`：最多总共试两台。不加这个限制，三台全挂的时候会连试三次，延迟翻倍，而且对后端是雪上加霜。

这里有个必须讲明白的因果关系：**我们停掉一台后端，九次请求全部成功，但最慢一次 5007 毫秒。** 这个 5 秒不是玄学，就是 `proxy_connect_timeout 5s` 到点了。那个请求被 `least_conn` 或轮询选中了一台已经死掉的实例，连不上，等 5 秒超时，才重试下一台。这个数字和配置能一一对上，讲的时候要把它对上。

### 4. 限流

两套东西，作用不同。

`limit_req` 管**速率**，用的是漏桶。`rate=8r/s` 是填充速率，`burst=20` 是桶的容量。桶里攒着的请求可以一次性放出去，但这会让瞬间压力直达后端，所以配 `nodelay`——不排队、直接放行，超出桶容量的当场拒绝。这三个参数组合的结果就是：一瞬间最多放过 21 个（1 个基准 + 20 个突发），其余返回 429。我们实测 40 并发里 21 个 200、19 个 429，就是这条配置的直接结果，不是巧合。

不配 `nodelay` 的话，超出的请求会被压住排队，每秒放 8 个，客户端等得久但可能全部成功。这是"拒绝"和"延迟"的取舍，两种都合理，看你更怕 429 还是更怕慢。

`limit_conn` 管**并发连接数**，`limit_conn conn_limit 20` 是每个 IP 最多同时 20 条连接。防的是慢连接占坑、单 IP 开几百条连接这类情况。

限流键的选择很关键。我们用 `$binary_remote_addr`，因为网关是唯一入口，它看到的就是真实客户端地址。**如果以后前面加 CDN，这个前提就没了**——所有请求的来源都会变成 CDN 的地址，等于把全部用户当成一个人限流。那时候必须上 `realip` 模块，从 `X-Forwarded-For` 里取真实地址，并且只信任 CDN 的地址段。这条边界现在不用做，但必须知道。

状态码这件事值得单独说。nginx 默认返回 503。503 的语义是"服务端现在不能处理请求"，客户端和中间的负载均衡器会理解成后端故障，进而在别处重试——错误的信号。429 的语义是"你请求太多"，客户端应该降低频率。所以显式写 `limit_req_status 429`。另外 429 可以带 `Retry-After` 告诉客户端等多久，我们没配，算一个小改进项。

### 5. 共享状态（zone）

`upstream` 里写 `zone symbiont_backend 64k`，是在共享内存里给这个地址池开一块区域，把每台的连接数、失败计数、健康状态放进去，让所有 worker 进程看到同一份。

不写 zone 会怎样？每个 worker 各自维护一份计数。请求量小、连接恰好分散在不同 worker 上时，看起来就是请求总落在第一台，另外两台闲着。而且服务完全正常，所以很难发现——它不是故障，是配置没生效。这属于"看起来能跑但没按设计跑"的典型。

排查方法不看可用性，看分布。跑十二次请求，三台的命中次数各四次才算对。

`zone` 的大小跟后端数量有关，64k 够几十台用。

### 6. 健康检查

分被动和主动。

**被动**：不额外发探测请求，靠真实请求的结果判断。某台连续失败 `max_fails=2` 次，就标记为不可用，`fail_timeout=10s` 之后重新放回池里试。这套机制的优点是零额外开销，缺点是**发现故障总是滞后的**——必须等真实请求失败才能知道。

滞后的代价就是我们那个 5 秒。想缩短它只有两条路：

- 把 `proxy_connect_timeout` 调短，比如 1 秒。代价是慢后端更容易被误判成故障——如果后端只是启动慢或者偶发卡顿，1 秒就把它判死，会造成误摘除和抖动。
- 换带主动探测的实现。开源的 nginx 没有主动健康检查，这是 Plus 版的功能；Envoy、HAProxy、OpenResty 配 lua、或者第三方的 `nginx_upstream_check_module`（要自己重编译）都能做到周期性探活，失败立刻摘、恢复立刻加。

这是成熟方案之间真正的差距所在，不在配置写法上。讲的时候把它摆出来，比讲十行配置有分量。

## 四、负载均衡：算法、门槛、以及为什么不粘

### 算法

- **轮询**：按顺序发。后端同构、请求耗时接近时最省心。缺点是慢请求会占住某个节点，后面的请求继续往上堆。
- **加权轮询**：按权重发。适合机器配置不同。缺点是权重靠人估，流量结构一变就得重调。
- **least_conn**：发给当前连接数最少的一台。它比轮询更能抗慢请求，因为慢的那台连接数会累积上去，自然少接新活。这是我们选它的理由：后端同构，但业务耗时差得远——保存档和查排行榜不是一个量级。
- **ip_hash**：按客户端地址取模。用来做会话保持。缺点是用户分布不均时会倾斜（比如校园网出口一个 IP 后面几百人）。我们不用它，因为不需要粘性会话。
- **hash / 一致性哈希**：按某个键（URL、用户 ID）散列到固定节点，用来提高缓存命中率。节点增减时普通取模会全盘重排，一致性哈希只影响邻近的一段。节点少的时候均衡效果一般，实现也更复杂。
- **random two choices**：随机挑两台，选负载低的那台。集群规模大时效果接近最优，Envoy 常用。规模小的时候没必要。

### 两个门槛

容量和可用性不是一件事，这是最容易混的地方。

**容量**：单台算不过来。判断不能靠感觉，要靠压测。把请求量和延迟画出来，会看到一个拐点——利用率超过七成左右，延迟开始非线性上升（排队）。这时候加机器才有意义。还有个粗算公式（Little 定律）：并发 ≈ 每秒请求数 × 平均延迟。所以 8 r/s、30 毫秒延迟，理论并发只有 0.24，一台后端绰绰有余。

**可用性**：不能因为一台故障就中断服务。这跟流量无关。哪怕一天三个用户，只要服务不允许中断，就该有第二台。

这两件事的台阶完全不同。把"我们流量小"当成"不需要第二台"的理由，是把两个问题揉成一个。比较诚实的说法是：入口那一层是必须的，负载均衡这一层是可用性需求，不是容量需求。

### 为什么不粘

粘性会话（sticky session）是让同一个客户端固定落到同一台后端，把会话状态留在那台的内存里。它解决的是"后端有状态"这个问题，代价是一堆新问题：那台挂了会话就丢、扩缩容要重新分布、调试时行为依赖命中哪台。

我们的后端是无状态 REST，账号、存档、排行榜都在 MySQL 里，任何一台都能处理任何请求。所以根本不需要粘性会话。**这是加副本不用改代码的前提**，也是设计上最省事的一步——在写代码的时候就把状态挪出去，比事后配粘性会话便宜得多。

### 代价要一起报

健康检查那一节说了，被动检查让故障切换有 5 秒代价。讲实测数据的时候，成功率和延迟必须一起报。只报"九次全部成功、成功率 100%"会让人以为切换是无感的，那是把问题藏起来。真实系统里这种"偶发的长尾延迟"恰恰是最难排查的东西。

## 五、你这份配置，逐块能讲什么

126 行，其实是八个决策，讲的时候按决策讲，不要逐行念。

**明文入口只做跳转。** `listen 8080` 上只有一个 `return 308`。用 308 不用 301，是因为 308 会保留请求方法和请求体，POST 跳到 https 之后仍然是 POST，不会退化成 GET。

**HTTPS 入口。** `listen 8443 ssl` 加 `http2 on`。容器里用非特权端口，宿主机映射到 443，这样网关进程不用 root 跑。这是安全实践，讲出来是加分项。

**TLS 参数。** 只开 1.2 和 1.3，砍掉 1.0/1.1（已经被认为不安全）。开了会话缓存，减少重复握手。

**指纹收敛。** `server_tokens off` 只抹掉版本号，`Server: nginx` 这三个字母还在。要彻底去掉得装 `headers-more` 模块。这一点要主动说清楚，不然被追问会尴尬。

**跳转补全。** `absolute_redirect off` 是关键的一行。默认 nginx 会把 `Location` 补成绝对地址，而它知道的端口是容器内的 8443，补出来就是 `https://localhost:8443/`，浏览器直接连不上。这个坑只有实际跑起来才会遇到。

**安全响应头。** 四个头放在 server 层，全部带 `always`。`always` 的作用是让 4xx/5xx 响应也带上这些头——默认只有 2xx/3xx 才加。还有一个继承规则要记住：**location 里只要出现任何一个 `add_header`，server 层这一整组就全部失效**。所以这些头必须放在 server 层，或者在每个 location 里重复写一遍。

**缓存分级。** `/game/` 下 `expires -1` 不缓存入口页，因为入口页要能立刻更新；`.wasm` / `.pck` 这些带内容哈希的产物给 30 天。这里有个匹配顺序的知识点：正则 location（`~*`）的优先级高于普通前缀 location，所以 pck 和 wasm 实际命中的是 30 天那条，不是 `/game/` 那条。

**反代那一块。** `proxy_pass` 走地址池、长连接三件套、四个转发头、重试策略、三个超时。上面都讲过了。

**日志格式。** `rt=$request_time urt=$upstream_response_time ua=$upstream_addr` 这三个字段是排障的核心：总耗时、后端耗时、落到哪台。差值大说明问题在网关或网络，`urt` 大说明问题在后端。重试发生时 `urt` 和 `ua` 会是逗号分隔的多个值。想更细还能加 `$upstream_connect_time` 和 `$upstream_header_time`，把连接和后端处理分开看。

## 六、可能被追问的问题，以及答法

**你们真需要负载均衡吗？**
不需要，按容量算一台就够。三台是为了验证这条路走得通，也是为了可用性——服务不许中断，就该有第二台。真要扩容，瓶颈会立刻转移到 MySQL，不是 uvicorn。

**为什么用 least_conn 不用轮询？**
后端同构，但业务耗时差距大。存档上传和排行榜查询不是一个量级，最少连接更抗慢请求，也不像加权轮询那样依赖人工估权重。

**限流为什么是 429 不是 503？**
503 表示服务端不可用，客户端会去别处重试，信号是错的。429 表示请求过多，客户端该降频。nginx 默认 503，必须显式改。

**限流键为什么用 IP，不怕被绕过或者误伤？**
网关是唯一入口，看到的 IP 就是真实的。加 CDN 之后必须换 realip，并且只信任 CDN 段。同一个 NAT 后面的用户会被合并计算，这是 IP 限流的固有缺陷，要按用户限流得在应用层做。

**被动健康检查和主动有什么区别？**
被动靠真实请求失败来判断，发现滞后，代价就是我们那个 5 秒。主动是周期性探活，能提前摘除，开源 nginx 没有，要 Plus、Envoy 或者第三方模块。

**网关自己挂了怎么办？**
网关是新的单点。消除它有几种做法：DNS 轮询到两台网关、两台加 keepalived 虚拟 IP、或者前面再放一层云负载均衡。这超出了本次范围，但要承认它是单点。

**自签证书能上线吗？**
不能，只适合演示和本机验收。正式环境要用 CA 签发的证书，并且做自动续期（ACME），再考虑 HSTS。

**大包为什么内存不涨？**
因为默认的代理缓冲是小块内存加溢出落盘，静态文件走 sendfile 零拷贝。严格意义上的零缓冲要关 `proxy_buffering`，对大响应和流式场景才有意义。

**HTTP/2 有什么用？**
一个 TCP 连接上多路复用，几十个首屏资源不用开几十条连接，省握手和头部。代价是 TCP 层的队头阻塞，HTTP/3 用 QUIC 解决。

**为什么用容器内非特权端口？**
网关不以 root 运行，减少逃逸风险。宿主机映射 80/443 是 docker 做的，容器里可以是 8080/8443。

## 七、三处可以坦白说的地方

讲技术最容易失分的是把话说满。这三处主动承认，比被问出来强。

第一，`server_tokens off` 只抹版本，抹不掉 "nginx" 这三个字母，要彻底去掉得装模块。

第二，网关自身是单点，本次没有解决。

第三，被动健康检查的 5 秒是真实代价，我们没消除它，只是量出来了。

还有一处口径要修正：早期材料里写"整块缓冲会把内存顶满"，这不准确。默认是缓冲到临时文件，内存不会顶满，代价是磁盘 IO 和首字节延迟。讲的时候用准确的说法。

## 八、上台前要能脱口而出的东西

- 一句定位：代理是唯一入口，策略只有放在唯一入口上才成立。
- 一条因果：5 秒 = `proxy_connect_timeout`，请求打在死实例上等超时。
- 一个数字：21 个 200、19 个 429，来自 8 r/s 加 burst 20 加 nodelay。
- 一个前提：源站不出内网，否则策略全可绕过。
- 一处取舍：容量要等流量，可用性不等流量。
- 一处诚实：被动检查的代价就是那一次五秒。
- 一个常识：keepalive 必须配 http 版本和空 Connection 才生效。
- 一个坑：`add_header` 在 location 里出现会覆盖 server 层整组。

这八条能顺口说出来，现场基本不会卡。
