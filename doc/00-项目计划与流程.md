# 00 项目计划与流程

## 一、目标

1. 游戏可玩：三层地牢、双流派（献祭流/探索流）、三结局（人类/异化/真 HE）、存档可用、无致命 bug；
2. 后端 FastAPI + MySQL：REST 有 OpenAPI、pytest 全绿、数据真实入库；
3. `docker compose -f deploy/docker-compose.yml up -d` 一键拉起，浏览器可玩 Web 版；
4. 课程 7 份文档（doc/01–07）+ 数据库脚本（database/）齐备；
5. CI 绿、main 保护、PR review、README 完整。

## 三、范围决策

| 方案 | 内容 |
|---|---|
| A（最小） | 只游戏 + SQLite 管道 + Web nginx，技术面偏薄 |

后端与客户端解耦（网络层离线优先），中途改 A/B 不影响游戏开发。

## 七、协作规则

1. main 保护，禁直接 push；每任务一个 feature/xx 分支 → PR → ≥1 人 review → CI 绿合并；
2. 设计文档先行：agent 只实现任务卡内容，不发明功能、不改接口、不调数值；
3. 手感/剧情决策永远是人；
4. 数值全部参数化，代码不写死；
5. 每周日提交实施周报（内部流程）；
6. 文档与代码注释用中文。

## 八、Agent 工作方式

上次失败原因：一次性做整个游戏、无验收、手感美术失控。本次：

1. 任务卡制：每任务一张卡（内部流程），含输入、实现要求、验收标准、禁止事项、产出；
2. 小步验收：每个任务独立分支 + 可运行检查点，CI 兜底；
3. 人机分工：agent 写代码与测试；人做设计、审核、试玩、手感调优；
4. 上下文交接：游戏设计 GDD 与任务卡是 agent 的"记忆"，开工先读相关章节。

任务卡为内部工作文档（移出仓库，组内保存）。
