# 标准与规范

本文件把大家一起干活要遵守的规矩写下来，共四部分：协作规范、编码规范、文档规范、数据规范。人人通读，干活时对照。对应老师本周要求的"标准成文"。

## 一、协作规范（怎么用 Git、怎么分工）

1. 开工前先更新：在项目文件夹运行 `git pull`，把线上最新代码拉到本地。
2. 干完活上传：依次运行 `git add .` → `git commit -m "..."` → `git pull` → `git push`。顺序不能变，pull 必须在 push 前面，防止覆盖别人的改动。
3. 提交信息格式：`类型: 干了啥`。类型用 feat（新功能）/ fix（修 bug）/ docs（文档）/ chore（杂项）。
   - 好例子：`feat: 加了玩家移动`、`fix: 修了跳跃穿墙`
   - 坏例子：`更新`、`修改`、`fix`
4. 红线：不用 `git push -f`；不删别人的文件；不跳过 `git pull` 直接 push。
5. 冲突处理：文件里出现 `<<<<<<<` 符号 = 你和别人改了同一处。别乱删，截图发群里，组长帮你合并。
6. 合并与审核：大改动先发群里说一声再合并；小改动可以直接推 main（按上面流程）。
7. 任务节奏（重要）：**一次只做一张任务卡（docs/tasks/）**。每张卡流程固定：agent 实现 → 无头验证跑通 → 合并 main → 组长试玩验收 → 组长说"通过"才开下一张。绝不一口气堆整个游戏，方便随时修 bug。
8. 周报：每周日提交到 docs/weekly/，命名 `组2-共生之缚-实施周报-日期`。

## 二、编码规范（怎么写代码）

1. GDScript：缩进 4 个空格；类名大驼峰（PlayerController），变量小驼峰（moveSpeed），常量全大写（MAX_HP）。
2. 注释用中文，写"为什么这么写"，不写废话。
3. 数值不写死在代码里：攻击力、血量、速度等进 `database/game_data`（或 data JSON）。改数值 = 改数据文件，不碰代码。
4. Python（tools/、server/）：缩进 4 个空格，函数名小写下划线（get_item）。
5. 新增信号 / 接口前，先看 docs/02 有没有现成的，有就复用；新增了要同步更新 docs/02。

## 三、文档规范（文档放哪、怎么命名）

1. 课程交付文档：docs/00 到 docs/07，编号对应老师要求，不挪位置。
2. 设计文档：docs/design/（GDD、决策日志）。
3. 任务卡：docs/tasks/，每个任务一张，用模板写。
4. 周报：docs/weekly/。
5. docs/02 接口文档是唯一权威：代码里的信号、接口和它不一致时，以它为准并同步修改代码。
6. 文档用中文、markdown 格式；大标题下直接写正文，不写小字引用块。

## 四、数据规范（数据怎么改）

1. 游戏内容数据源是 `database/game_data/*.sql`。改数据 = 改 SQL 文件。
2. 改完跑两步：`python tools/build_game_data.py`，再 `python tools/db_export.py`，生成 JSON。
3. `client/data/` 下的 JSON 是生成物，禁止手改。
4. 服务器数据库脚本在 `database/schema.sql` 和 `seed.sql`；改表结构要同步改 `server/app/models.py` 和 docs/03 的 ER 图。

## 五、开工默认动作

- 每天开工：先 `git pull`
- 打开游戏：Godot 打开 `client/project.godot`，按 F5
- 提交前：运行 `git status` 看一眼自己改了哪些文件
