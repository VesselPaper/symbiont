## 一、分析建模的常用工具

**目的**：把"想法"变成"画得出来、说得清楚"的模型，方便组内对齐、老师评审、照着写代码。

**我们怎么分工**：先用人脑 + 传统工具把图画对，再用 AI 工具快速生成初稿、补齐遗漏，最后人工审校定稿。两张工具一起用，谁快用谁。

### 1.1 传统工具（画图 + 文档）

| 工具 | 用途 | 我们实际用在哪 |
|---|---|---|
| StarUML / Draw.io (diagrams.net) | 画 UML 类图、用例图、状态图 | 类图、用例图（也用于评审时现场改图） |
| PlantUML | 用文字描述画图，好版本管理 | 时序图、活动图的文字源 |
| 白板 / 便利贴 | 需求研讨、功能划分 | 03、04 文档的研讨过程 |
| Excel / 表格 | 数据项、功能清单登记 | 02 功能点拆分、本文件数据项清单 |
| Markdown | 文档统一载体 | 全部 class1 文档 |

### 1.2 AI 工具（提效 + 查漏）

| 工具 | 用法 | 我们实际用在哪 |
|---|---|---|
| AI 画图助手 | 把自然语言需求转成 PlantUML / Mermaid 代码，再生成图 | 先出用例图、状态图初稿，再人工校核 |
| AI 需求分析助手 | 从功能描述里抽数据项、关系、约束 | 本文第三节数据项初稿 |
| AI 代码助手 | 把图/模型转成 SQL、GDScript 骨架 | schema.sql、后端 models.py 初稿 |

**经验**：AI 快但会编，画完的图必须回到需求上一项一项对；数据项清单必须对着真实代码文件（schema.sql / models.py / 存档代码）核对，不能只信 AI 输出。

## 二、常用图：怎么画、画给谁看

老师要求的三种核心图，我们已在 `uml/` 出图，说明如下。

### 2.1 用例图（系统对外提供什么）

- 看 `uml/用例图.png`。
- **给谁看**：用户、老师。表达"谁（角色）能对系统做什么（用例）"。
- **我们画了什么**：游客/账号玩家/组员三类角色；游玩、教学、献祭、存档、远程同步、看排行榜等用例；玩家-账号的泛化关系（游客登录后升级为账号玩家）。

### 2.2 类图（系统内部有什么数据、谁跟谁关联）

- 看 `uml/后端类图.png`（后端领域模型）。
- **给谁看**：开发。表达"有哪些对象、对象有哪些属性、对象之间什么关系"。
- **我们画了什么**：User / SaveData / GameEvent / LeaderboardEntry 四个模型，User 与其余三者 1 对多关联；属性直接对应后端数据表字段。
- **为什么重要**：类图 = 数据项的第一现场，第二节数据项清单就是从它和 schema.sql 抄下来的。

### 2.3 状态转换图（对象有哪些状态、怎么变）

- 看 `uml/教程状态图.png` 和 `uml/游戏状态图.png`。
- **给谁看**：开发。表达"某个东西有几个状态、什么事件让它切换"。
- **我们画了什么**：游戏全局状态机（BOOT → 主菜单 → 游戏中 → 结局/结束，可暂停）和教程的 10 个教学状态（触碰光点/拾取/受击/击杀/献祭驱动前进）。
- **为什么重要**：状态图直接指导代码里的状态机实现，教程状态图对应的代码已在 main 验收通过。

## 三、需求分析关键点：数据项清单（重点）

**为什么数据项是重点**：需求分析讲"要做什么"；数据项讲"要存什么、传什么"。表结构、存档格式、接口字段全由数据项决定。下面分三块：游戏内容数据（静态）、存档数据（动态）、后端数据（联网）。

### 3.1 游戏内容数据（静态，SQL 管）

来源：游戏内容库 SQL 文件（schema.sql，版本 v1，改表必须同步改导出和 DataDB）。

| 数据项 | 关键字段 | 示例值 | 对应需求 |
|---|---|---|---|
| items 物品 | id、name、type、stats、obtain、flags | iron_sword / 钩锁 / 蒸汽靴 / 怪物肢体 | F-05、F-12 |
| enemies 敌人 | id、name、hp、speed、behavior、attack_damage、drops | 巡逻史莱姆 / 孢子射手 / 守门 Boss | F-03、F-12 |
| npc NPC | id、name、faction、location | 异教徒祭司 / 工程师 | F-04、F-13 |
| dialogues 对话 | id、npc_id、lines(JSON)、next_id、branch | intro_parasite_1 → intro_parasite_2 | F-04 |
| endings 结局 | id、name、condition、weight | refuse_die / human / transformed / true_he | F-11、F-14 |
| sacrifices 献祭改造 | id、part、route、effect(JSON) | arm_claw / leg_taint | F-12、F-13 |

**数据项关系**：对话挂在 NPC 下（dialogues.npc_id → npc.id）；物品/敌人都有 drops/obtain 字段把"掉什么、从哪拿"串起来；结局由存档里的献祭次数等数据触发。

### 3.2 存档数据（动态，客户端存）

来源：客户端存档系统代码（save_system.gd + game_manager.gd），存档 Schema v1。

| 数据项 | 类型 | 说明 | 是否已实现 |
|---|---|---|---|
| version | int | 存档格式版本（当前 1，迁移用） | ✅ |
| saved_at | string | 保存时间 | ✅ |
| game_progress.sacrifice_count | int | 献祭次数（结局结算依据） | ✅ |
| game_progress.monster_limb_count | int | 怪物肢体持有数 | ✅ |
| game_progress.current_floor | string | 当前楼层（floor_1/2/3） | ✅ |
| game_progress.faction | string | 阵营（""/heretic/engineer） | ✅ |
| game_progress.flags | dict | 通用剧情旗标 | ✅ |
| player | dict | 玩家位置/血量/能力（M1 填） | ⏳ |
| inventory | dict | 背包与已改造部位（M1 填） | ⏳ |
| levels | dict | 楼层进度：开关/已拾取/已击败（M2 填） | ⏳ |

### 3.3 后端数据（联网，MySQL 管）

来源：后端数据模型代码（models.py，与内容库/后端 schema 一致），四张表。

| 表 | 关键字段 | 说明 | 状态 |
|---|---|---|---|
| users | id、username(唯一)、password_hash、created_at | 账号 | ⏳ M2 |
| saves | id、user_id→users、slot、save_data(JSON)、updated_at | 远程存档，每用户每槽一条 | ⏳ M2 |
| events | id、user_id(可空)、event、payload(JSON)、created_at | 统计埋点 | ⏳ M2 |
| leaderboard | id、board、user_id→users、score、meta(JSON)、created_at | 排行榜 | ⏳ M2 |

**数据一致性约定**：
1. 游戏内容数据"一处改 SQL，导出成 JSON 给游戏读"，运行时 JSON 禁止手改；
2. 存档 Schema v1 同时约束客户端本地档和后端 saves.save_data；
3. 数据项变了，先改 SQL/代码，再更新本文档和系统接口设计文档。
